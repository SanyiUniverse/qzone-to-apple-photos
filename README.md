# QQ 相册迁移到 Apple Photos

面向 Apple Silicon Mac 的本地迁移流程：复用现有 QQ 相册下载项目，以 ExifTool 检查和修复导入副本，再使用 macOS Photos 原生接口分批导入、核对日期与相册归属。

目标是保留 QQ 仍提供的最高质量媒体、未经修改的下载备份，以及现有证据支持的拍摄／创建时间。QQ 页面上的上传日期仅作为来源记录，不用于拍摄日期回退。QQ 已经压缩、转码或丢弃的信息无法凭空恢复。

**已在 Apple Silicon Mac、Photos 11.0 上完成真实整库迁移及逐项核验，先通过 12 项 JPEG、PNG、GIF、MP4 样本，再处理有可靠拍摄时间的项目。照片与视频的 Photos 日期精确到秒匹配来源，相册归属及未修改原片 SHA-256 均通过；无法确认时间或当前图库状态的项目保留备份和 QQ 来源。另完成了明确授权的 QQ 精确白名单清理。换系统、图库、账号或规则后仍需重跑自己的样本；通用入口的合成测试不能代替本机实测。**

需求与方案选择见 [需求和验收标准](docs/requirements.md)。AI 接手时先读 [AGENTS.md](AGENTS.md)，再按下文执行；仓库不包含任何真实照片、账号或个人迁移记录。

下次可以直接把这个仓库交给能操作本地 Mac 的助手，说明“按 AGENTS.md 为我的账号执行迁移，先样本、再全量；缺失拍摄时间的资料暂缓”。助手复用现有入口与私有日志，普通 QQ 登录由你在官方页面完成。是否清理 QQ 来源需另行明确，不能从迁移请求推定。

## 方案来源

按以下顺序调查并复用，避免另写一套下载应用：

1. [11273/QzonePhoto](https://github.com/11273/QzonePhoto)：先审查原图选择、时间逻辑和原件保留。审计的 v2.7.0 存在布尔设置回退问题：`false` 被当成缺省值，可能使已关闭的元数据写入重新启用。因此没有把该版本未经修改的写入路径当作“原样备份”方案。具体范围见[元数据说明](docs/metadata.md#上游实现的边界)。
2. [dslwind/qzone-photo-downloader](https://github.com/dslwind/qzone-photo-downloader)：复用已有登录/API/下载能力和 QQ 日期字段解析思路，固定上游提交；避免其原位修改下载件的行为。适配范围及许可见 [THIRD_PARTY.md](THIRD_PARTY.md)。
3. [ExifTool](https://exiftool.org/)：直接检查和写入具体日期字段，不重新编码图片或视频。
4. macOS Photos 原生脚本接口：按明确相册和资产 ID 导入、读回、调整图库日期及导出未修改原片。

本项目只补齐备份、证据记录、少量元数据修复和批量核验，不提供新的账号系统、云服务或大型桌面应用。

## 按有来源的拍摄／创建时间排列

| 日期 | 用途 | 保存位置 |
| --- | --- | --- |
| 原文件或 QQ 仍保留的拍摄／创建时间 | 媒体元数据与 Photos 日期的目标 | 原件、导入副本中的相应 EXIF/QuickTime 字段、证据记录；必要时设置 Photos 图库日期 |
| QQ 相册页面的上传时间 | 追溯上传记录，不作为拍摄时间回退 | 私有来源清单 |

二者可能相差多年。实测 QQ 页面的上传展示时间与拍摄时间不同，因此本流程排除 `uploadtime` 和上传语义的 `modifytime` 回退；缺少拍摄时间时不以下载当天补齐。

转发图、编辑图或截图中的日期，最多是当前证据支持的最接近素材产生时刻的时间，不是对真实拍摄时刻的绝对保证。明确截图名称中的创建时间可以作为标明来源的低置信推断；普通文件名、上传日期名称和下载时间均不作为拍摄证据。来源冲突、缺失或只有日期时保留待处理，不虚构时分秒。

## 使用前准备

- Apple Silicon Mac、Apple Photos、Google Chrome、Python 3.11 或更新版本。上游登录由 Selenium 打开官方 QQ 网页；无需安装 PyQt 图形界面。
- ExifTool 在命令搜索路径中。已有可用版本就复用；可从[官方页面](https://exiftool.org/)安装，已有 Homebrew 时可用 [Homebrew 安装方式](https://formulae.brew.sh/formula/exiftool)：`brew install exiftool`。
- 足够保存下载原件、导入副本、Photos 图库和完整原片导出校验的空间；导出校验可能额外占用接近一份媒体的空间。另准备独立备份位置。
- 只迁移有权读取和保存的自己的相册。在官方网页内扫码或自行登录，不把密码交给脚本或 AI。源码与私有数据目录分开；QQ 原始响应也包含隐私和临时媒体链接。
- 明确 Photos 当前打开的目标图库。样本和后续全量必须使用同一图库及记录；不要中途切换系统照片图库或 iCloud 设置。

## 执行流程

1. **清点与取证。** 保留相册/项目映射、原始文件名、媒体类型、QQ 原始 API 日期字段、页面显示日期、时区依据和可用下载版本。将上传时间与拍摄相关来源分别记录；登录 Cookie 仅在会话内存中使用，不保存密码或 Cookie。原始响应及其中可能存在的临时签名媒体链接只保存在私有输出目录。
2. **原样下载。** 优先 QQ 的原图/原视频地址；没有原件时记录实际可用版本。根据文件内容识别格式，不能把视频封面当视频成功，也不能仅因扩展名是 `.jpg` 就认定为 JPEG。
3. **建立不可变备份。** 原始响应字节单独保存并计算整文件 SHA-256。后续只编辑导入副本，保留原件及其完整元数据快照。
4. **挑选约 10–15 个样本。** 覆盖不同年份、实际存在的格式、照片和视频、有/无内嵌日期、字段冲突及接近午夜的项目。
5. **最小修复。** 只补充有证据的缺失或错误日期；保留相机、镜头、GPS、方向、色彩配置及其他原有标签。规则见[元数据说明](docs/metadata.md)。
6. **原生导入与读回。** 当前流水线每批最多 50 项，按源相册分组，保存 Photos 返回的 ID；按唯一文件名或导出字节证明建立映射，核对日期和相册成员关系。
7. **验证排序与质量。** 对照选定的拍摄／创建来源和 Photos 信息窗；GIF 等必要情况仅调整 Photos 图库日期，并保存旁车记录。样本从 Photos 导出未修改原片，验证文件哈希；修复前后验证媒体内容哈希和非日期元数据。
8. **样本通过后全量。** 按已验证规则分批处理，逐批持久化日志和映射；遇到新格式、字段冲突、下载失败或不确定结果，暂停相应项目。完成后核对清单、成功/失败/未处理项，以及备份可读性。

### 1. 准备环境

从源码根目录运行；把示例 QQ 号码替换成自己的账号，并选容量足够的私有目录。不要把以下各阶段连成无人审阅的一条命令。

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

umask 077
export QQ_OWNER="你的QQ号码"
export QZONE_MIGRATION_OUTPUT="$HOME/Pictures/QQ-Photos-Migration"
mkdir -p "$QZONE_MIGRATION_OUTPUT"
exiftool -ver
```

所有命令复用同一私有目录，不放入源码仓库。当前规则以 QQ 的 `+08:00` 展示约定为基础；它不是对所有素材历史拍摄时区的认定。已有内嵌偏移量会保留；其他地区或旅行素材必须先核对时区。

### 2. 清点并下载 12 项样本

```sh
python collect.py --owner "$QQ_OWNER" --output "$QZONE_MIGRATION_OUTPUT"
python sample_selection.py --output "$QZONE_MIGRATION_OUTPUT" --count 12
python batch_download.py --selection "$QZONE_MIGRATION_OUTPUT/sample.json"
python batch_download.py --selection "$QZONE_MIGRATION_OUTPUT/sample.json" --download
```

`collect.py` 只收集相册、每页原始响应和视频详情链接，不下载媒体。首次在打开的官方网页登录；完整缓存可复用时不重复登录或请求清单。Cookie 只在会话内存中使用，结束时清除。确需刷新才加 `--refresh`，旧响应会归档；开始导入后不要未经核对刷新相册映射。

选择器覆盖不同年份、照片和视频，并优先加入 PNG/GIF 等格式线索。检查私有 `sample.json`，补上实际存在但遗漏的格式、日期冲突或接近午夜的样本。API 格式线索最终仍以下载后的实际文件类型为准，不应只挑容易通过的项目。

`batch_download.py` 不带 `--download` 只显示范围。下载复用上游函数和缓存 URL；视频必须匹配同一 `picKey`，封面不计为视频成功。原字节逐项保存、计算 SHA-256 并设为只读；已经通过哈希验证的原件会复用。原名称、稳定来源身份和实际使用的 URL 字段类别保留在私有记录中。

### 3. 检查时间计划，再生成副本

```sh
python prepare_capture.py
python prepare_capture.py --apply
```

第一次只检查原件并写计划／缓存，不改媒体。先审阅 `迁移记录/拍摄时间准备计划.json` 中的来源、精度、时区、冲突和视频处理推断，再执行第二次生成导入副本。每项检查媒体内容不变、原有非目标元数据仍在。

只有 `capture_ready` 项允许导入；`unknown`、`date_only`、`needs_review` 等项目暂缓。样本阶段只下载样本，因此准备清单只包含这些项目，尽管输出文件名包含“全量”。不要事先下载整库后直接对整份清单执行样本导入。

### 4. 导入样本并导出验证

```sh
python photos_pipeline.py --sample \
  --journal "$QZONE_MIGRATION_OUTPUT/迁移记录/Photos样本导入"
python photos_pipeline.py --sample --apply \
  --journal "$QZONE_MIGRATION_OUTPUT/迁移记录/Photos样本导入"
```

默认只显示计划；`--apply` 才操作 Photos。首次可能需允许系统“自动化”权限。`--sample` 要求 5–15 个可入库项目，清单含照片和视频时两者必须覆盖；每次都重新导出全部样本的未修改原片验证 SHA，不复用旧的导出证明。合格项不足或缺少覆盖时补齐样本，不绕过门槛。

还需在 Photos 查看信息窗、跨年排序、图片方向、GIF 动画和视频画面／声音。脚本只有日期、相册和原片哈希验证通过后才写 `迁移记录/Photos样本最终验证.json`。不要手工写入 `passed`，也不要把下载成功当作样本通过。被暂缓的候选另列，不能算已迁移。

### 5. 样本通过后的全量阶段

确认样本结论和授权范围后，再执行：

```sh
python batch_download.py --download
python prepare_capture.py
python prepare_capture.py --apply
python photos_pipeline.py --export-verify
python photos_pipeline.py --apply --export-verify
```

保持同一目录、来源映射、日期规则和图库。下载复用已验证原件，准备流程复用已验证检查点，Photos 流程先读回样本和已记录资产，再处理剩余项。全量示例明确开启 `--export-verify`：12 个样本的哈希结果不能代替全量原片证明。

全量 `--export-verify` 要求每项都有完整导出 SHA 证明，不意味着每次续跑都重导出所有文件。每次续跑仍重新核对导入副本 SHA 和 Photos 当前日期、相册成员等信息；只有来源身份、资产 ID、SHA、秒级日期、目标相册实际 ID 及名称、文件名与成员关系全部和旧证明一致，且证明文件仍在，才复用旧证明。新项或不满足条件的项目必须重新导出；样本模式始终重新导出。详情见[证明复用规则](docs/workflow.md#完整导出证明的复用)。

全量完成需要逐项核对：源总数等于已验证迁移项加明确暂缓／失败项；来源、资产 ID、日期和相册映射正确；全部已迁移项导出 SHA 通过；下载原件仍可读且哈希未变。新格式、冲突和失败不会因总进度达到 100% 自动算成功。中断恢复见 [docs/workflow.md](docs/workflow.md)。

## 已观察到的兼容性边界

- 有效的图片 EXIF 拍摄时间经导入后可以保留；没有可识别日期的项目可能落在下载或导入当天，仅修改文件名不能解决。
- JPEG/PNG 等支持的图片副本可用 ExifTool 补充有证据的 `DateTimeOriginal`。HEIC 等未在同一测试环境覆盖的格式必须另测，不能从 JPEG 推论。
- 某个 MP4 实测采用非零 `QuickTime:CreateDate`，没有采用新写入的 `Keys:CreationDate`。仅写 Keys 不足以保证 Photos 日期正确，不能把旧版社区经验当成固定优先级。
- GIF 保持原始编码；没有可靠的跨应用拍摄日期写入方案时，采用 Photos 图库日期和外部证据记录。导出 GIF 原片不会自动携带图库日期。
- 原生导入在开启重复检查时可能出现确认框；脚本超时不代表尚未导入。当前流水线显式配置 `skip_check_duplicates: true`，由来源映射和持久化记录防止本任务重导；它不会去重图库中原有的同内容照片。

这些是有限样本的实测结论，具体证据边界见 [docs/metadata.md](docs/metadata.md)。

## 中断与重复项目

每次导入之前记录计划，导入后立即保存返回的资产 ID、文件名和源项目映射。导入/导出发生超时或数量不符时，先核对日志与指定任务相册，不重跑整批，也不要删除日志绕过保护。

源相册按稳定 ID 分开，目标名为 `迁移QQ相册之“源名称”`；同名源相册依次加 `（2）`、`（3）`，不合并。文件名尽量保留，清理文件系统非法字符、补实际扩展名并加短 ID 防覆盖。QQ 已丢失的相机原始文件名无法恢复。

Photos 对内容相同的文件可能沿用另一资源的文件名。不能只因名字不同判为错图，也不能无条件忽略差异；按明确资产 ID 导出原片，以 SHA、目标日期和相册成员证明映射。不能按返回数组顺序猜测，不能仅按 SHA 去掉不同源相册中的项目。

修正后的样本重导曾在确认旧测试项已移入“最近删除”后仍出现重复确认。遇到这种情况先核实对话框及明确文件集合。Photos 中的删除与移除相册成员不同；回收测试项目时保留“最近删除”的恢复能力。

当前自动批处理使用 `skip_check_duplicates: true`，由已持久化的 QQ 项目映射和导入日志防止本任务重复导入。这可能为用户图库中原先存在的同内容照片创建另一份资产，不会替用户清理重复内容。超时后不能通过改重复检查选项盲重跑，仍须先确认哪些项目已经入库。

只有确认不存在的项目才重新导入。核验时必须按指定相册过滤 ID；本机发现 `album.mediaItems.byId(...)` 本身不能证明相册成员关系，原生 `exists()` 也出现类型转换错误。

## 暂缓项目与 QQ 清理

**默认不删除 QQ 内容。** 没有拍摄时间、只有日期或仍有冲突的项目保留原件和来源记录、暂缓导入。用户要求单独交付时，可把这些项目及清单复制到指定桌面文件夹，逐项验证复制 SHA；原备份和 QQ 来源仍保留。

在准备清单已经生成后，可运行以下独立备份命令。它立即复制暂缓原件和经过筛选的来源说明，不需要 `--apply`，不访问 QQ 或 Photos：

```sh
python hold_pending.py \
  --manifest "$QZONE_MIGRATION_OUTPUT/迁移记录/全量拍摄时间导入清单.json" \
  --destination "$HOME/Desktop/QQ-Photos-Pending"
```

重复运行会验证并复用相同副本，不覆盖内容不同的同名文件。桌面目录也属于私有资料，不可提交仓库。

QQ 清理是单独、明确授权的可选收尾动作，仅限正常导入且完成完整导出 SHA 验证的具体项目。现有 QzonePhoto 的删除实现已复用为最小适配，增加精确白名单、当前 Photos 核验与异常对账。默认不开启删除；不得整相册删除、包含暂缓项或清空回收站。具体命令见[可选来源清理](docs/workflow.md#可选来源清理)。
