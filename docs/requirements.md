# 解决的需求与验收标准

把自己 QQ/Qzone 的照片和视频迁移到 Apple Photos，尽可能保留素材产生时刻、现存元数据、最高可下载质量及原相册结构。整个流程在自己的 Mac 上运行，公开仓库只放通用实现和说明。

## 已确认的需求

| 需求 | 方法与通过条件 |
| --- | --- |
| 优先现成方案 | 按 QzonePhoto → dslwind → ExifTool 的顺序审查；复用下载核心和已有删除接口，只补最小协调与验证 |
| 原件备份 | 保存 QQ 返回的原始响应字节、文件 SHA 和下载规格；设为只读，另建导入副本 |
| 拍摄时间 | 比较内嵌日期、`originalTime`、`rawshoottime`、`shoottime`、详情 `shootTime` 与上传时间；选择有证据的拍摄/创建候选，保留冲突与精度 |
| 排除上传日期兜底 | QQ 查看器展示的上传时间、普通日期文件名、下载时间均不能补造拍摄时刻 |
| 无质量损失 | 不重编码、不为日期改格式；修复前后验证媒体内容哈希与非目标标签，Photos 导出未修改原片再比整文件 SHA |
| 保留相册 | 按源相册 ID 映射为 `迁移QQ相册之“原名”`；同名源相册用编号区分，分别核对完整成员集合 |
| 先测试再全量 | 约 12 个跨年、跨格式样本；读回日期精确到来源支持的秒数、核对相册与哈希，少量检查图像/GIF/视频播放 |
| 无法恢复的资料 | 单独备份原件和原因，暂缓导入；QQ 来源继续保留，不填写虚构日期或 GPS |
| 已验证后的来源清理 | 只有用户明确要求才启用；精确白名单、当前 Photos 状态、原件与副本哈希再次通过后逐批处理 |
| 可接续运行 | 调用前写日志，之后保存实际 ID 与证据；超时先对账，不把“请求失败”当成“完全没发生” |

## 实际方案为什么这样选

被审计 QzonePhoto 版本的日期写入与设置回退不能直接满足“未经修改原件单独保留”的要求。dslwind 提供了足够的登录、列表、下载与日期读取基础，但其上传时间回退、原位 JPEG 写入和视频日期处理仍需隔离。最终复用 dslwind 下载能力，交给 ExifTool 修改副本，以 Photos 原生接口完成导入与验证；可选清理复用 QzonePhoto 的现成接口。

图片主要补有来源且缺失的 `DateTimeOriginal`；`CreateDate` 是数字化时间，不无条件复制拍摄时间。视频同时检查 QuickTime 容器、轨道/媒体日期及 Keys 字段，本机实测仅加 Keys 日期不足以保证排序。GIF 保持原字节，必要时采用有来源的图库日期并保存旁车。

QQ 已经剥离或压缩的信息无法恢复。相机参数只补 QQ 仍提供的缺失字段；无证据的相机时区、GPS、亚秒、拍摄日期不猜测。详细字段规则与实测限制见 [metadata.md](metadata.md)。

## 完成的定义

下载、导入、来源清理分别核算。每个源 ID 必须落入已验证、明确暂缓或明确失败的一类；不能把总进度或相册数量作为完成证据。图库中后来被删除的资产退出来源清理白名单，等待用户处理；不得未经确认恢复用户可能主动删除的照片。

发布通用实现前运行合成测试并逐文件检查隐私；新账号重跑真实样本。不要将当前仓库的测试通过标记复制到另一账号作为验收结果。
