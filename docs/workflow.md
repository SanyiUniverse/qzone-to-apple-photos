# 运行记录、恢复与可选收尾

命令顺序见 [README](../README.md)，日期规则见 [metadata.md](metadata.md)。本文解释如何判定完成、安全恢复，以及明确授权后执行可选 QQ 清理。

## 私有目录与身份

所有命令通过 `QZONE_MIGRATION_OUTPUT` 使用同一私有输出目录。收集阶段用 `collect.py --owner` 指定自己的账号，后续下载复用缓存，不需要把 Cookie 写到磁盘或重新调用清单 API。可选 QQ 清理需要新的有效普通 QQ 登录，并再次检查登录账号与来源账号相同。

| 内容 | 用途 |
| --- | --- |
| 下载原件及逐项 `*-download.json` | 原始字节、SHA、实际格式、来源字段、下载版本、相册与项目 ID |
| `迁移记录/QQ原始响应` | 每页清单／视频详情的原响应和解析结果；仅供本地审计 |
| `迁移记录/相册映射.json` | 源相册 ID、原名称、数量和目标相册名称 |
| `sample.json` | 明确的样本 `(album_id, pic_key)` 列表 |
| `迁移记录/拍摄时间准备计划.json` | 选择的日期来源、精度、时区、冲突和拟修改字段 |
| `导入副本` 与准备检查点 | 已通过媒体内容及元数据核验的导入文件 |
| `迁移记录/全量拍摄时间导入清单.json` | 当前所有已下载项目的准备结果；样本阶段也使用这个文件名，不代表已处理整库 |
| `迁移记录/全量拍摄时间待确认.json` | 非 `capture_ready` 项；未知、仅日期和冲突不能归入迁移成功 |
| `迁移记录/Photos样本最终验证.json` | 样本通过凭证，绑定来源、资产、日期和导出哈希 |
| Photos 操作日志中的 `batch-*` | 调用前请求、返回 ID、逐项核验、导出和完成记录 |
| Photos 操作日志中的 `verified-ledger.json` | 当前已核验资产及来源映射；完整导出证明还须查看每批的 `export_verified`、`export-verification.json` 与对应证明引用 |

所有这些内容都是私有交付资料，不能提交到公开仓库。只读文件权限可防止误改，但不等于独立备份；至少另存一份下载原件和必要清单后再考虑来源清理。

## 两类重复不能混为一谈

**同名相册。** 同一名字可能对应多个 QQ 相册 ID。流程为它们建立不同目标名，首个 `迁移QQ相册之“源名称”`，随后 `迁移QQ相册之“源名称”（2）` 等，并将对应关系持久化。开始导入后保留这份映射。Photos 原有多个同名目标相册时会出现歧义，不能任取一个。

**内容相同的素材。** 同一个文件可能出现在多个相册，甚至名称不同。来源映射必须按相册 ID 与项目 ID 保存，不能仅按文件名或 SHA 去掉源项目，否则会丢失相册归属。

Photos 返回顺序不保证等于导入顺序；对相同内容还观察到资源文件名沿用另一资产的名称。程序先尝试相册内唯一名称映射，必要时按实际返回的资产 ID 导出原片，以 SHA、目标日期和相册成员关系证明对应。多个来源的字节、目标时间和相册均等价时，记录等价来源集合并采用确定性分配；不声称从相同字节反推出历史上的唯一原文件名。

当前 `photos_pipeline.py` 显式使用 `skip_check_duplicates: true`，因此不会等待 Photos 的重复确认框；本任务的重导防护依赖来源映射与日志。这不是全图库去重，不能删除用户原先已有资产。

## 发生中断后

1. 先确认中断的是下载、准备副本还是 Photos 调用。保留当前目录，不删除 `.json` 或重新建空日志绕过检查。
2. 下载只复用文件存在且 SHA、格式及记录一致的原件；下载不完整或格式无法识别的项目不是成功。链接失效才考虑显式刷新缓存，并重新核对来源映射。
3. 已存在导入副本需有匹配的准备检查点和 SHA，不能静默覆盖。媒体哈希或非目标元数据改变时，定位原因后重新准备明确范围。
4. Photos 的 `pending.json` 和操作请求在调用前写入。原生调用超时不意味着没有入库。先看返回的资产 ID、指定迁移相册及导出的原片；只读核对后恢复记录，不直接重导。
5. 有完整返回 ID 但文件名映射失败时，可以对这些 ID 导出原片核对。返回 ID 不完整时必须查清已入库集合，不能根据相册总数猜测。
6. 某个日期错误时查明是元数据、时区还是 Photos 读取优先级。GIF 或已获验证的特定格式可以调整图库日期；不要把修正所有图库日期当作掩盖未知来源的捷径。

重导测试需要删除旧样本时，仅处理此次测试映射确认的资产，保留“最近删除”的恢复能力。移除相册成员和从图库删除不是同一个操作。不要清空最近删除来解决重复问题。

### 恢复未完成的 Photos 批次

对日志中已经返回完整资产 ID 的批次，使用现有 ID 核验和重新导出即可恢复证明。以下示例路径需要换成实际未完成批次，不能指向已完成批次：

```sh
python photos_recover.py "$QZONE_MIGRATION_OUTPUT/迁移记录/Photos批量导入/batch-00042"
python photos_recover.py "$QZONE_MIGRATION_OUTPUT/迁移记录/Photos批量导入/batch-00042" --apply
```

第一条只读日志并显示计划；第二条读取现有资产的日期/成员、导出原片验证 SHA，然后生成真实完成证明。两条都不会重新导入、修改日期、删除或恢复资产。旧版本的纯核验批次若没有保存 `known_assets`，可增加 `--known-ledger /绝对路径/先前verified-ledger.json` 指定已有身份来源。

如果返回 ID 不全、不唯一或相互矛盾，入口在原生操作前停止。保留日志，按明确任务相册内的原片 SHA、日期和来源建立映射后单独审查；它不会按数量/返回顺序猜测缺失项。日期修正本身中断时也不会偷偷修改图库日期，必须先查明来源与当前状态。

最终流水线会用 `photos_album_audit.js` 读取任务相册完整 ID 集合。缺失项写入 `pending_recovery` 并退出当前成功数；额外资产、同名相册歧义或相册身份变化会阻止最终确认。已标记待恢复的项目即使重新出现，也须经复核解除，不能自动进入 QQ 删除白名单。

### Photos 返回成功但导出目录为空

实际运行曾遇到 Photos 原生导出返回成功、目标目录却没有文件；重新打开 Photos 后，对原有资产重新执行导出恢复正常。这是本次环境中的恢复经验，不是所有导出失败的通用修复，也不说明照片尚未导入。

当前校验会先最多等待 30 秒让文件落盘，只对完全缺失的导出自动再尝试一次，并使用新的独立目录。已有文件但数量、大小、SHA、日期或相册归属不符，不当作“缺文件”反复重试；空目录的成功响应永远不算原片证明。

如果仍为空：

1. 保留原请求、返回资产 ID、失败目录和 `export-proof.json`。不删除整个批次日志，不重新导入，不将批次手工改成已完成。
2. 检查 Photos 当前窗口，确认没有正在进行的导入、编辑、未保存更改或等待用户处理的对话框。需要用户处理的编辑／对话框先处理；不能自动点“放弃更改”，不能用强制退出绕过它。
3. 确认应用可以正常退出后，正常关闭并重新打开同一图库。不要在这一步换图库、重置图库或调整 iCloud 设置。
4. 只对已记录且成员关系核对通过的资产 ID，向新的导出目录重新导出未修改原片，再验证 SHA、日期和相册。保留前次失败证据与本次恢复证据；只有这些检查全部通过才完成该批次并继续。

公开流程不自动退出用户的 Photos。必要的人工恢复是导出核验操作，不能变成删除、重导或全图库重新扫描。

## 如何证明画质未变

证明链必须完整：

1. 下载原件 SHA 与保存记录一致，处理前后未改变。
2. 修复副本若字节变化，其 ExifTool `ImageDataHash` 与原件相同，原有非目标语义元数据仍在。若无可用媒体内容哈希，只能接受整文件字节未变，或暂停并建立适合该格式的独立验证。
3. Photos 按指定资产 ID **导出未修改的原片**；每项独立导出目录中的文件整 SHA 等于实际导入副本。不能拿普通导出、拖出的预览或修复前原件代替比较对象。

因此，修复后的导入副本与下载原件整文件 SHA 不同可能是正常元数据变化；Photos 导出原片与导入副本 SHA 不同则不能记为通过。保留两组哈希及修改字段，不能只保存“成功”文字。

样本的 12 项验证只证明这些格式和处理分支在该环境通过。全量命令必须包含 `--export-verify`，每个已迁移项目均有原片证明，才能用于后续清理白名单。日期核验也需要逐项进行，不能只检查最早／最晚年份或相册数量。

### 完整导出证明的复用

全量 `--export-verify` 的含义是每个合格项目都有完整原片导出 SHA 证明。它允许续跑复用严格匹配的既有证明，避免对同一已验证资产反复导出全部媒体；这不减少任何项目的证明覆盖。

每次续跑先重新计算当前导入副本 SHA，并通过 Photos 原生接口重新读取当前日期、文件名、资产和相册成员关系。旧证明只有同时满足以下条件才可复用：

- 来源 `(album_id, pic_key)` 与记录完全一致。
- Photos 资产 ID、导入副本 SHA、目标秒级时间均与当前核验值一致。
- 目标 Photos 相册实际 ID、目标名称、当前资源文件名均一致，且旧记录和当前查询都证明资产在该相册内。
- 引用的已通过样本或已完成批次证明文件仍然存在。

新资产、没有证明或任一条件不一致的项目进入新的原片导出核验。`--sample` 始终为全部样本重新导出，不采用此优化。文件名别名不能豁免这些条件；先建立字节证明，并保留实际文件名后才能参与严格比较。

每批的 `export-verification.json` 分别记录复用的证明、此次新导出的来源，以及本次原生读回结果；`completed.json` 保存 `export_proof_references`。不要删除被引用的证明文件、把仅有总数的报告当作逐项证明，或因为旧证明通过就跳过当前日期／成员查询。已有导出文件可以按收尾规则去除冗余副本，但原始备份和完整证明链必须保留。

## 暂缓项目的桌面备份

用户要求暂存时，从当前待确认清单精确选取项目，复制其未经修改原件和对应来源记录到指定桌面文件夹。每项核对复制 SHA 与下载记录，附上缺失／冲突原因、已有日期精度和原相册归属。路径可以由用户选择，不在代码中硬编码。

```sh
python hold_pending.py \
  --manifest "$QZONE_MIGRATION_OUTPUT/迁移记录/全量拍摄时间导入清单.json" \
  --destination "$HOME/Desktop/QQ-Photos-Pending"
```

该命令没有 `--apply` 开关，调用即执行本地复制。它只选择非 `capture_ready` 项，保存 `说明.md` 和 `暂缓项目清单.json`，不会复制原始 API 响应或下载 URL，也不会修改媒体。已有副本先核对 SHA，内容不同的同名文件不覆盖；旧备份不会自动删除。清单仍含来源身份和私有路径，不是公开报告。

暂缓表示未完成迁移，不表示无价值或可以丢弃。原下载备份、QQ 来源和精确身份映射继续保留；不导入为当天，不把未知时间补成午夜，不将该文件夹作为“删除所有剩余 QQ 项”的依据。

## 可选来源清理

默认不执行。只有用户明确要求，并且以下条件已经逐项满足，才建立独立的删除白名单：

- 有未经修改原件及验证后的备份；来源稳定身份明确。
- Photos 当前资产 ID、目标日期和目标相册成员关系均核验正常。
- 该项已完成未修改原片导出，整文件 SHA 与实际导入副本相同。
- 不属于未知、仅日期、冲突、失败或桌面暂缓集合。

白名单键为 `(album_id, pic_key)`，而不是名称、日期或数量。不要删除整个相册，即便其中绝大多数项目已迁移。仅报告批次成功数量也不够，需要逐 ID 成功结果并重新读取清单，确认已删集合和保留集合。

优先检查现成工具。被审计的 [QzonePhoto v2.7.0](https://github.com/11273/QzonePhoto/blob/038e1beb38a230246dde3824f8f0ada3bf4a98ea/src/main/api/qzone/photo.js#L291-L352) 已有 `cgi_delpic_multi_v2`，按单相册和明确项目 ID 批量删除；[界面选择逻辑](https://github.com/11273/QzonePhoto/blob/038e1beb38a230246dde3824f8f0ada3bf4a98ea/src/renderer/src/views/photo/components/main.vue#L1141-L1217) 使用 `lloc/picKey/id`。它没有本迁移的验证白名单，也不逐项证明全部成功；视频参数覆盖和接口可用性需要实际核实。dslwind 被审计版本没有删除功能。

能够确保精确选择时可使用现成工具或 QQ 官方批量管理；否则暂停清理，不能为了省操作改成全选。不要添加一个默认执行的删除阶段，也不要在公开代码放 Cookie、QQ ID 或个人白名单。成功删除后仍保留本地原件与证据，不自动清空 QQ 或 Photos 回收站。

### 已验证的清理边界

本机实际清理使用了 QQ 原生“放入回收站”确认及 QzonePhoto 既有 `cgi_delpic_multi_v2` 的最小适配，包含图片与视频。普通 QQ 扫码登录足够执行本次清理；独立空间密码是在进入回收站查看或恢复时要求的，不是本次正常删除的必要条件。其他账号应先核对自己当时的回收能力与提示，不能从接口名称推定永久可恢复，也不提供清空回收站功能。

每批最多 50 项：读取当前 QQ 来源集合 → 验证原件/导入副本 SHA 与冻结的 Photos 证明一致 → 读取当前 Photos ID、日期与相册 → 为新文件名别名导出字节补证 → 写入持久化意图 → 提交一次请求 → 再读 QQ 清单并核对消失的精确 ID 集合。一个批次的成功响应不能代替最后一步。

超时、代理错误或响应无法解析时立即停止后续删除，只能先只读 `reconcile`。对账确认仍存在的 ID 才能形成新的明确批次；已消失的项目记入台账，不能把整个原请求自动重试。部分成功也需要按当前集合重新计划，不按请求次数累加完成数量。

Photos 中后来被移入“最近删除”的资产保留 QQ 来源，不自动恢复或重新导入。冻结证明、准备清单、原件、副本、任务相册或 QQ 来源集合发生变化时，先解释和重新核验；不要删除日志绕过保护。

### 可选清理命令

先完成全量 `--export-verify` 和当前相册集合核验，再运行本地白名单构造。它检查证明及原件，不访问 QQ，也不会删除数据：

```sh
python cleanup_plan.py --output "$QZONE_MIGRATION_OUTPUT"
python cleanup_plan.py --output "$QZONE_MIGRATION_OUTPUT" \
  --commands "$QZONE_MIGRATION_OUTPUT/迁移记录/QQ清理核验/commands-001.jsonl" \
  --batch-size 25
```

默认读取 `Photos批量导入/verified-ledger.json`；使用其他日志目录时通过 `--ledger` 指定同一私有记录目录下的实际文件。`--manifest`、`--plan` 可指定已审阅的对应路径。已存在白名单或命令文件不覆盖；不能重建空台账来忽略既有删除结果。生成命令只列出已核验且尚未删除的 ID，不提交请求。

默认会话只允许清点和对账：

```sh
python cleanup_session.py --owner "$QQ_OWNER" --output "$QZONE_MIGRATION_OUTPUT"
```

只有账号主人已明确授权、且当前 QQ 界面已确认所选照片和视频的回收语义时，才加 `--allow-delete --recycle-bin-confirmed`。该会话在官方 Chrome 页面登录，Cookie 只在内存中。等待 `READY` 后，一次提交一个 JSON 命令：

```json
{"cmd":"inventory"}
```

每个 `delete_batch` 使用刚生成的私有 JSONL 中明确的相册、ID、集合摘要和确认标记。只有上一批返回 `delete_batch_verified` 且实际消失集合完全一致后，才发送下一批。不要把整个命令文件直接管道输入并假设全部成功。

出现不确定结果后发送 `{"cmd":"reconcile"}`，它只读 QQ 实际集合；确认仍存在的 ID 才可重新生成新命令文件。最后再发送 `{"cmd":"inventory"}`，应恰好得到保护集合且白名单剩余为零；完成后 `{"cmd":"quit"}` 清除会话内存。会话过期时重新普通扫码登录并先对账，不需要在聊天或配置里提供密码。

## 完成报告与收尾

分别报告：选择的工具和固定版本、采用的日期来源、保留及补充的元数据、照片／视频的实测结果、全量已验证数量、暂缓／失败数量及原因、备份位置，以及是否真的执行过独立授权的来源清理。

下载完成不等于迁移完成；样本通过不等于全量通过；QQ 清理不属于默认完成标准。结束前关闭本任务创建的临时浏览器、进程和预览，清理已不需要的重复导出及缓存前先确认完整核验记录和必要备份保留。不要清理无关文件或用户原有会话。

完成后可去除用作 SHA 核验的重复导出媒体，以免长期占用第二份图库空间：仅从本任务 `export-request.json` 中的明确 `export_dir` 枚举，核对路径归属、非符号链接和文件属性后处理已验证副本。不能递归清空“迁移记录”；JSON 请求、结果、哈希证明、原件、导入副本及暂缓备份继续保留。清理后重新检查这些保留物和引用证明存在。
